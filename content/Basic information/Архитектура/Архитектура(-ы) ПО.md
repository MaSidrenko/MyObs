[[Многослойная архитектура]]



Красивые Цитаты:
1) "Цель Архитектуры ПО - понизить связанность кода", что равносильно управление зависимостями.
2) «Архитектура» — это способ формирования систем для достижения нефункциональных целей (масштабируемость, надёжность, гибкость).



Семейство многослойных архитектур ПО:
1) многоуровневая(N-уровневая)
2) Чистая Архитектура
	Почему вам не нужна чистая архитектура?
		https://habr.com/ru/articles/888428/
	Акцент на уровни абстракции впихимаемые тупо везде.
	В остальном равносильна Луковой архитектуре(у неё нету акцента а абстракки)
3) Луковая архитектура
	Акцент на внутреннею организованность кода, на точную иерархию слоёв.
	Я бы лично сказал на всеобщею организованность кода.
4) Гексагональная архитектура
	aka "Порты и адаптеры"
	Акцент на организации связей с внешними к приложению объектами:
		Базы данных, интеграции с облачными сервисами, UI и т.д.
	По личному мнению, видимо Луковая включат в себя гексагональную,
		где гексагональная является упрошенным вариантам Луковой.



Микросервисы
1) Ключевая идея: разделить функционал приложения на разные приложения (сервисы, Микросервесы)
2) Если одно из приложений упадёт - остальные продолжат работать, и выполнять полезную нагрузку
3) В идеале - может даже не быть Core сервиса.
	1) Не отменяет того факта, что какие то сервисы могут быть критичными, и будут стопорить 90% функционала всего приложения
4) За счёт того что код первоначально делится на сервисы, то есть отдельные модули, так же позволяет легче реализовывать горизонтальное масштабирование.
	1) За счёт горизонтального масштабирования, реализуется защита от того что какая то нода в сервисе упадёт: так как остальные ноды будут выполнять полезную нагрузку
	2) Балансировщики для нод тоже можно масштабировать \ резервировать горизонтально.
5) Так же одна из киллер фич, это удобное деление разработки между командами.



Монолиты:
	Обобщённое название для любой архитектуры, когда при разработке приложения не было строгих регламентов по архитектуре.
	Структурированные монолиты подразделяются на:
		1) Модульные монолиты:
			Функционал делится на модули (файлы)
			Внутри модуля может быть каша, однако общение между модулями более строго контролируется инженерами, хотя может осуществляться без строгого регламента.
		2) Плагинные приложения:
			1) Что то среднее между микросервисами и многослойными архитектурами:
			2) Монолит выступает в роли Ядра, которое представляет API для плагинов.
			3) Плагины могут быть как "DLL-like" расширениями Монолита, так и быть контейнерами и общаться по виртуальной сети.
				1) Ключевая особенность: 
					1) если Core приложение упало
					2) плагин не может выполнить даже часть полезной нагрузки \ функционала

Архитектуры \ Потерны API
	Слишком большая тема, для которой нужна отдельная заметка.

Про API и Вызовы функций.
1) У API есть сходство с вызовами функций, которые происходят внутри приложения.
2) Разница между ними одновременно очевидна и нет.
3) Наиболее обобщённым разделением будет вопрос:
	1) Насколько вызов этой функции безопасен относительно текущего контекста?
	2) Если безопасность высокая - то перед нами функция
	3) Если нет - то нам надо провести ряд инженерных махинаций, которые сделает эту функцию допустимо безопасной. Реализация этих махинаций и будет созданием API.
4) Небезопасность возникает по разными причинам:
	1) Серверный код и клиентский код могут иметь разные версии
	2) Механизм вызова, например работа с сетью, может предполагать отсутствия соединения, что необходимо учитывать \ обрабатывать.
		1) Необходимость обрабатывать ошибки или возвращаемое значение вызова - тоже характерная черта для API.
	3) Если у нас есть секретные данные, или сложная политика безопасности, нам может потребоваться спроектировать API, для работы с чувствительными к ИБ данными.
	4) Методы в библиотеке - своего рода тоже API.
		1) Мы хотим обезопасить внутренний код, поэтому доступ к нему осуществляется через ограниченный API. (хранилище секретов на 3) пункте - случай из того же семейства
		2) Методы в библиотеке так же часто предполагают обработку возвращаемого значения или ошибок.
5) Резюмируя: API это реализация небезопасных функций безопасно.
